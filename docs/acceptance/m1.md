# M1 Pairing and Device Link acceptance

**Status:** BLOCKED pending a dual-homed Setup client and one clean-commit real-Deck run.

Tracking: [M1 specification #20](https://github.com/Vectorking-50kg/s3-rlcd-deck/issues/20), [acceptance #31](https://github.com/Vectorking-50kg/s3-rlcd-deck/issues/31).

The acceptance command builds the current clean commit, safely programs and verifies both Deck
OTA application slots, validates the firmware and Companion embedded commit identities, starts
the real Companion, and uses the real Deck Setup page, pinned
TLS/WSS client, persisted Companion Profile, and management routes. It proves first Pairing,
Deck reboot reconnection, Companion stop/recovery, wrong-certificate rejection, incompatible
major rejection, trust revocation, and management/Device Hub authority separation. It also
links a same-commit Actions run in which both native macOS and Windows tray observations passed.

The controller Mac never leaves its normal LAN. A separate Linux Setup client must have a
NetworkManager-managed Wi-Fi interface and an independent wired interface on the same LAN as the
Mac. The controller reaches that client over SSH on the wired interface. For each Setup session,
the helper joins the Deck AP, proves that `192.168.4.1` uses Wi-Fi while the Companion address uses
the wired interface, and first returns the current Profile snapshot in an independent transaction.
Only after the controller has recorded that compensation state does the helper open a temporary
TCP relay to the real Companion, read the recovery page, submit the six-digit code, consume the 202
response, and acknowledge its single-use capability.
It then deletes its non-persistent NetworkManager connection and restores its prior Wi-Fi state.
Before any NetworkManager mutation it writes a mode-0600 journal containing only the original and
temporary connection UUIDs. Every controller request is followed by a new SSH `cleanup` transaction
that replays this journal idempotently and proves both the original active connection and absence of
the temporary profile. A per-transaction cross-process lock and persistent cancellation fence
prevent the new cleanup process from racing—or being overtaken by—a delayed primary process. The
preflight also requires NetworkManager to classify the SSH
interface as Ethernet; a second Wi-Fi, bridge, or tunnel cannot claim the `wired` gate. A timeout or
dropped SSH channel therefore cannot make cleanup pass locally.
This preserves ADR 0007's rule that initial trust is established by the actual Setup-AP peer.

Copy `tools/m1_setup_client.py` from the commit under test to the Linux client. Create an ignored
local JSON file containing only the helper argv, for example:

```json
["ssh", "-T", "m1-helper", "python3", "/opt/s3deck/m1_setup_client.py", "--wifi-interface", "wlan0", "--control-interface", "eth0"]
```

The controller compares the remote helper's SHA-256 with its local file before builds or flashing,
and every subsequent snapshot, Pair, restore, and cleanup request repeats that same identity check
before any network mutation.
Setup credentials and the Pairing code travel only in the SSH process's standard input. The helper
passes the WPA PSK to NetworkManager through a mode-0600 FIFO and uses `connection add save no`;
neither secret appears in a process argv or a regular file. See the official
[NetworkManager nmcli reference](https://networkmanager.dev/docs/api/latest/nmcli.html) for the
non-persistent connection and `passwd-file` semantics.

Raw evidence remains under ignored `.hil-results/`. Only the machine `summary.json` may be
copied to `docs/acceptance/evidence/`. The serial capture is allow-listed and redacted: Setup
access is replaced by a fixed marker, and credentials/certificates are never persisted.

Failures return non-zero and keep only the partial redacted capture and summary. A missing,
wrong-version, single-homed, or unreachable Setup client fails before preflight and app flashing.
Companion output,
preflight output, app-flash output, and serial evidence all pass the redaction gate. A compensating
cleanup restores Deck trust, closes Setup, restores the helper's prior Wi-Fi state, stops every
Companion process, and makes any cleanup failure fail the run. The Mac network is never modified.
Host replay or fake adapters cannot set the real Deck or native platform gates.

The current version-controlled report remains blocked until the result is produced from the
same clean commit as both firmware and Companion.
